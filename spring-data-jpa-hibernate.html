    6.3.2. Spring-Konfiguration

     

    Die Klasse [ConfigJpa] konfiguriert das Spring-Projekt:

    
package generic.jpa.config;

import javax.persistence.EntityManagerFactory;

import generic.jdbc.config.ConfigJdbc;

import org.apache.tomcat.jdbc.pool.DataSource;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Import;
import org.springframework.orm.jpa.JpaTransactionManager;
import org.springframework.orm.jpa.JpaVendorAdapter;
import org.springframework.orm.jpa.LocalContainerEntityManagerFactoryBean;
import org.springframework.orm.jpa.vendor.Database;
import org.springframework.orm.jpa.vendor.HibernateJpaVendorAdapter;
import org.springframework.transaction.PlatformTransactionManager;

@Configuration
@Import({ ConfigJdbc.class })
public class ConfigJpa {

    // der Provider JPA
    @Bean
    public JpaVendorAdapter jpaVendorAdapter() {
        HibernateJpaVendorAdapter hibernateJpaVendorAdapter = new HibernateJpaVendorAdapter();
        hibernateJpaVendorAdapter.setShowSql(false);
        hibernateJpaVendorAdapter.setDatabase(Database.MYSQL);
        hibernateJpaVendorAdapter.setGenerateDdl(true);
        return hibernateJpaVendorAdapter;
    }

    // Entitätspakete JPA
    public final static String[] ENTITIES_PACKAGES = { "generic.jpa.entities.dbproduitscategories" };

    // Datenquelle
    @Bean
    public DataSource dataSource() {
        // Datenquelle TomcatJdbc
        DataSource dataSource = new DataSource();
        // Zugriffskonfiguration JDBC
        dataSource.setDriverClassName(ConfigJdbc.DRIVER_CLASSNAME);
        dataSource.setUsername(ConfigJdbc.USER_DBPRODUITSCATEGORIES);
        dataSource.setPassword(ConfigJdbc.PASSWD_DBPRODUITSCATEGORIES);
        dataSource.setUrl(ConfigJdbc.URL_DBPRODUITSCATEGORIES);
        // anfänglich offene Verbindungen
        dataSource.setInitialSize(5);
        // Ergebnis
        return dataSource;
    }

    // EntityManagerFactory
    @Bean
    public EntityManagerFactory entityManagerFactory(JpaVendorAdapter jpaVendorAdapter, DataSource dataSource) {
        LocalContainerEntityManagerFactoryBean factory = new LocalContainerEntityManagerFactoryBean();
        factory.setJpaVendorAdapter(jpaVendorAdapter);
        factory.setPackagesToScan(ENTITIES_PACKAGES);
        factory.setDataSource(dataSource);
        factory.afterPropertiesSet();
        return factory.getObject();
    }

    // Transaktionsmanager
    @Bean
    public PlatformTransactionManager transactionManager(EntityManagerFactory entityManagerFactory) {
        JpaTransactionManager txManager = new JpaTransactionManager();
        txManager.setEntityManagerFactory(entityManagerFactory);
        return txManager;
    }

}

    6.3.3. Die Entitäten der Schicht [JPA]

      

    Die Ziel-Datenbank ist die Datenbank [dbproduitscategories] mit ihren beiden Tabellen [CATEGORIES] und [PRODUITS]. Wir haben gesehen, dass sie außerdem drei weitere Tabellen namens [USERS, ROLES, USERS_ROLES] enthält, die zur Absicherung des Webdienstes dienen, der im Web bereitgestellt wird. Diese Tabellen lassen wir vorerst außer Acht. Zur Erinnerung noch einmal die Struktur der Tabellen [CATEGORIES] und [PRODUITS]:

    Die Tabelle [PRODUITS] sieht wie folgt aus:

    • [ID]: der autoinkrementierte Primärschlüssel der Tabelle [2];
    • [NOM]: der eindeutige Name des Produkts [4];
    • [PRIX]: der Preis des Produkts;
    • [DESCRIPTION]: die Produktbeschreibung;
    • [VERSIONING] ist die Versionsnummer des Produkts. Die ursprüngliche Version lautet 1 [3]. Bei jeder Änderung des Produkts wird die Versionsnummer durch den Code, der die Tabelle auswertet, erhöht;
    • [CATEGORIE_ID]: Der Fremdschlüssel in der Tabelle [CATEGORIES], der die Kategorie angibt, zu der das Produkt gehört;
    • in [1-3], der Fremdschlüssel [CATEGORIE_ID] der Tabelle [PRODUITS]. Sie bezieht sich auf die Spalte [ID] der Tabelle [CATEGORIES] [4-5];
    • wenn eine Kategorie gelöscht wird, werden alle damit verknüpften Produkte ebenfalls gelöscht ([6]). Dieser Punkt ist wichtig zu beachten, da er beim Aufbau der Ebene [DAO] verwendet wird, die auf der Datenbank [dbproduitscategories] basiert;

    Die Tabelle [CATEGORIES] der Kategorien sieht wie folgt aus:

    • [ID]: automatisch inkrementierter Primärschlüssel;
    • [VERSIONING]: Versionsnummer der Kategorie;
    • [NOM]: Eindeutiger Name der Kategorie;

    Wir werden nun die Entitäten JPA, [Produit] und [Categorie] aus den Tabellen [PRODUITS] und [CATEGORIES] beschreiben.

import generic.jpa.infrastructure.ProxyException;

import javax.persistence.Column;

import javax.persistence.Transient;
import javax.persistence.Version;

import com.fasterxml.jackson.annotation.JsonFilter;
import com.fasterxml.jackson.annotation.JsonIgnore;

@Entity
@Table(name = ConfigJdbc.TAB_PRODUITS)
@JsonFilter("jsonFilterProduit")
public class Produit implements AbstractCoreEntity {
    // Eigenschaften
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = ConfigJdbc.TAB_JPA_ID)
    protected Long id;

    @Column(name = ConfigJdbc.TAB_JPA_VERSIONING)

Man kann auch [@Entity(name="MonProduit")] schreiben, wodurch die Entität den Namen [MonProduit] erhält. Fehlt diese Angabe, lautet der Name der Entität der Name der Klasse, in diesem Fall [Produit].     • Zeile 22: Die Anmerkung [@Table(name = "PRODUITS")] gibt an, dass die Klasse [Produit] das Objektbild einer Zeile der Tabelle [PRODUITS] in der Datenbank ist;
    • Zeile 23: Der Name des Filters jSON, der auf die Entität angewendet werden soll. Wir werden sehen, dass die Eigenschaft [categorie] in Zeile 58 nicht immer verfügbar ist. Sie muss daher aus der Darstellung jSON des Objekts ausgeschlossen werden. Dazu benötigen wir einen Filter. In einem Filter mit dem Namen [jsonFilterCategorie] legen wir also fest, ob die Eigenschaft [categorie] berücksichtigt werden soll oder nicht;
    • Zeile 26: Die Anmerkung [@Id] legt fest, dass das mit der Anmerkung versehene Feld das Feld ist, das dem Primärschlüssel der Tabelle aus Zeile 19 zugeordnet ist;
    • Zeile 27: Die Annotation [@GeneratedValue(strategy = GenerationType.IDENTITY)] legt den Modus für die automatische Generierung des Primärschlüssels in der Tabelle [PRODUITS] fest. Dies wird durch das Attribut [strategy] bestimmt. Es gibt verschiedene Modi:

    Die Strategie [IDENTITY] ist nicht für alle SGBD verfügbar. Von den sechs getesteten SGBD war sie für die SGBD und [MySQL 5, PostgreSQL 9.4, SQL Server 2014, DB2 Express-C10.5] verfügbar. Für die beiden anderen [Oracle Express 11g Release 2, Firebird 2.5.4] musste die Strategie [SEQUENCE] verwendet werden. Für die Portabilität zwischen Implementierungen JPA darf nicht die Strategie [AUTO] verwendet werden, da diese die Wahl der Strategie zur Generierung des Primärschlüssels dem Ermessen der jeweiligen Implementierung JPA überlässt. Bei MySQL 5 und der Strategie [AUTO] gilt somit:

    • wählt Hibernate die Strategie [IDENTITY] mit dem Modus [AUTO_INCREMENT] für den Primärschlüssel;
    • wählt „EclipseLink“ die Strategie „[TABLE]“, die standardmäßig eine Tabelle namens „[SEQUENCE]“ erstellt, die abgefragt werden muss, um die Primärschlüssel zu erhalten.

    Letztendlich ist die von diesen beiden Implementierungen JPA verwaltete Datenbankstruktur nicht identisch. Wenn sie von Hibernate generiert wurde, kann sie nicht von EclipseLink verwendet werden und umgekehrt.

    • Zeile 28: Die Annotation [@Column(name="ID"] legt den Namen der Spalte in der Tabelle [PRODUITS] fest, die dem Feld [id] zugeordnet werden soll;
    • Zeile 29: Für den Primärschlüssel wird der Typ [Long] anstelle von [long] verwendet. Denn die Primärschlüssel [null] haben für JPA eine besondere Bedeutung. Daher wird hier lieber ein Objekttyp als ein einfacher Typ verwendet;
    • Zeile 31: Die Anmerkung [@Version] gibt an, dass das Feld [version] einer Versionsspalte zugeordnet ist. Die Implementierung JPA erhöht diese Versionsnummer jedes Mal, wenn die Entität geändert wird. Diese Nummer dient dazu, die gleichzeitige Aktualisierung der Entität durch zwei verschiedene Benutzer zu verhindern: Zwei Benutzer, U1 und U2, lesen die Entität E mit einer Versionsnummer von V1. U1 ändert E und speichert diese Änderung in der Datenbank: Die Versionsnummer ändert sich daraufhin zu V1+1. U2 ändert seinerseits E und speichert diese Änderung in der Datenbank: Es wird eine Ausnahme ausgelöst, da seine Versionsnummer (V1) von der in der Datenbank gespeicherten (V1+1) abweicht;
    • Zeile 36: Der Typ der Entität. Es gibt zwei davon: POJO und PROXY. Standardmäßig ist die erzeugte Instanz ein POJO (Plain Old Java Object). In bestimmten Fällen sind die aus der Datenbank abgerufenen Instanzen vom Typ [Produit] vom Typ [PROXY]. Dies ist der Fall, wenn die Eigenschaft [Categorie categorie] in Zeile 58 aufgrund des Attributs [fetch = FetchType.LAZY] in Zeile 56 nicht mit einer Kategorie initialisiert wurde. In diesem Fall unterscheiden sich die zu testenden Implementierungen JPA:
      • [Hibernate, OpenJPA]: Der Zugriff auf die Kategorie eines Produkts vom Typ [PROXY] löst eine Ausnahme aus. Hibernate bezeichnet eine Instanz vom Typ JPA, die im Modus [LAZY] abgerufen wurde, als „Proxy“. Aus diesem Grund habe ich diesen Begriff verwendet, um diese Art von Entität zu bezeichnen;
      • [EclipseLink]: Der Zugriff auf die Kategorie eines Produkts vom Typ [PROXY] führt dazu, dass in der Datenbank nach dieser Kategorie gesucht wird, und es tritt keine Ausnahme auf;

    Da ich eine von der verwendeten Implementierung JPA unabhängige Testebene haben wollte, wollte ich den Typ jeder Entität kennen: POJO oder PROXY. Deshalb habe ich das Feld [entityType] zu den Entitäten JPA hinzugefügt;

    6.3.4. Die Datei [persistence.xml]

      

    Die Anwendungen JPA müssen bestimmte Eigenschaften des verwendeten Anbieters JPA sowie die zu verwendenden Entitäten JPA in einer Datei [META-INF/persistence.xml] definieren, die sich im Classpath der Anwendung befindet. Im obigen Beispiel wurde sie im Ordner „[src/main/resources]“ abgelegt, der tatsächlich Teil des Classpaths eines Eclipse-Projekts ist. Bei der Verwendung von JPA in Verbindung mit Spring werden bestimmte Informationen, die eigentlich in der Datei [persistence.xml] enthalten sein sollten, an anderer Stelle in Spring-Konfigurationsklassen abgelegt. In einer Spring-Anwendung JPA steuert Spring die Datei JPA. Bei Spring JPA mit Hibernate lässt sich die Datei [persistence.xml] auf das Wesentliche reduzieren:

    
<?xml version="1.0" encoding="UTF-8"?>
<persistence version="1.0" xmlns="http://java.sun.com/xml/ns/persistence" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
    xsi:schemaLocation="http://java.sun.com/xml/ns/persistence http://java.sun.com/xml/ns/persistence/persistence_1_0.xsd">
    <persistence-unit name="dummy-persistence-unit" transaction-type="RESOURCE_LOCAL" />
</persistence>
    • Zeilen 1–5: Eine [persistence.xml]-Datei muss ein Stamm-Tag <persistence> enthalten. Die Attribute des Tags in Zeile 2 werden in dieser Anwendung nicht verwendet;
    • Eine Persistenzdatei kann eine oder mehrere Persistenzeinheiten mit dem Tag <persistence-unit> (Zeile 4) definieren. Eine Persistenzeinheit verwaltet den Zugriff auf eine bestimmte Datenbank. Wenn die Anwendung zwei Datenbanken gleichzeitig verwaltet, verfügt sie über zwei Persistenzeinheiten;
    • Zeile 4: Eine Persistenz-Einheit hat den Namen [attribut name], unterstützt den Transaktionstyp [attribut transaction-type], verfügt über Eigenschaften und definiert die Entitäten, die den Tabellen der von der Persistenz-Einheit verwalteten Datenbank zugeordnet sind. Da hier der Zugriff auf die Datenbank von [Spring JPA Hibernate] verwaltet wird, können diese beiden letzten Informationen an anderer Stelle platziert werden. Es gibt zwei Transaktionstypen:
      • [RESOURCE_LOCAL]: Die Transaktionen werden von der Anwendung selbst verwaltet. Dies ist hier der Fall, wo Spring die Transaktionen verwaltet;
      • [JTA] (Java-Transaktion API): Der Container EJB (Enterprise Java Bean), der die Anwendung ausführt, verwaltet die Transaktionen automatisch anhand der im Code gefundenen Java-Annotationen. Diese Konfiguration liegt hier nicht vor;

    Wir werden im Folgenden sehen, dass der Inhalt dieser Datei [persistence.xml] von der verwendeten Implementierung JPA abhängt.

Wir erinnern uns, dass in der Entität [Produit] das Feld [categorie] das Attribut [fetch = FetchType.LAZY] (Lazy Loading) hatte. In der Abfrage JPQL erzwingen wir das Laden der Kategorie mit dem Schlüsselwort [fetch];
    • Zeilen 18–19: Die Methode [getLongProduitByName] liefert die Langform eines Produkts, das durch seinen Namen identifiziert wird;
    • Zeilen 21–22: Die Methode [getShortProduitsById] liefert die Kurzversion der Produkte, die durch ihren Primärschlüssel [id] identifiziert werden. In dieser Kurzversion hat das Feld [categorie] nicht den Wert null. Es enthält die Referenz eines Proxys, der von der Implementierung JPA generiert wurde und der, wenn er aufgerufen wird, die Produktkategorie abruft. Dieser Aufruf kann nur im Persistenzkontext JPA erfolgen. Ein Aufruf an anderer Stelle löst eine Ausnahme aus (Hibernate und OpenJpa, jedoch nicht EclipseLink). Daher werden wir in der Schicht [DAO] oder anderswo das Feld [categorie] eines Produkts in seiner Kurzversion nicht verwenden. In der Kurzversion des Produkts wird das Feld [idCategorie] initialisiert. Sein Wert ist der Primärschlüssel der Kategorie, zu der das Produkt gehört. Dies ermöglicht es später, diese Kategorie über die Methode [DaoCategorie. getShortCategoriesById(idCategorie)] von der Ebene [DAO] abzufragen;

    • Zeilen 33–34: Die Methode [getAllLongProduits] gibt die Langform aller Produkte zurück;
    • Zeilen 36–37: Die Methode [getAllShortProduits] gibt die Kurzversion aller Produkte zurück;

    Diese Schnittstellen werden durch Klassen implementiert, die bei der Ausführung des Projekts von der Implementierung JPA generiert werden. Solche Klassen werden als [proxy]-Klassen bezeichnet. Standardmäßig werden die Methoden der Schnittstelle [CrudRepository] in einer Transaktion ausgeführt. Da die Schnittstellen [ProduitsRepository, CategoriesRepository] die Klasse [CrudRepository] erweitern, sind sie Spring-Komponenten. Als solche können sie in andere Spring-Komponenten injiziert werden.
